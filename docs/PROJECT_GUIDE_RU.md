## 1. Что делает проект

Это робот для физической версии игры «Арканоид». Мяч движется по реальному
полю, а каретка робота ездит по своей линии. Камера сверху снимает поле,
компьютер понимает, где сейчас мяч, примерно рассчитывает его путь и отправляет
каретке команду: ехать влево, вправо или остановиться.

Обычная работа не требует нейросети. Программа ищет мяч и метку робота по
выбранному цвету. Это хорошо подходит для контролируемого стенда: цвет мяча,
метки и поля можно сделать различимыми. В папке `tools/ml/` есть отдельные
эксперименты с YOLO, но они не нужны, чтобы робот начал ездить.

## 2. Как устроена система

```mermaid
flowchart LR
    A["Камера над полем"] --> B["Python: поиск цвета"]
    B --> C["Прогноз точки встречи"]
    B --> D["Поиск метки каретки"]
    C --> E["Регулятор движения"]
    D --> E
    E --> F["Bluetooth HC-06"]
    F --> G["Raspberry Pi Pico"]
    G --> H["Драйвер и мотор каретки"]
```

Роли частей простые:

- **Камера** даёт новые кадры поля несколько раз в секунду.
- **Python-программа** на компьютере находит мяч и робота, переводит их
  координаты в миллиметры поля и решает, куда двигаться.
- **Bluetooth HC-06** передаёт короткие текстовые команды.
- **Raspberry Pi Pico** выполняет команды и управляет выходами моторов.
- **Watchdog (сторожевой таймер)** в Pico останавливает привод, если компьютер
  завис, выключился или потерял связь.

## 3. Словарь простыми словами

| Слово | Что это означает без сложной математики |
| --- | --- |
| Кадр | Одна фотография от камеры. Видео — это много таких фотографий подряд. |
| OpenCV | Библиотека Python, которая умеет открывать камеру, работать с цветом и рисовать отладку. |
| HSV | Удобный способ хранить цвет: оттенок, насыщенность и яркость. По нему легче отличить цветной мяч от фона, чем по обычным RGB-числам. |
| HSV-маска | Чёрно-белая картинка: белое — пиксели подходящего цвета, чёрное — всё остальное. |
| Контур | Граница найденного белого пятна на HSV-маске. По ней программа отличает круглый мяч от случайного блика. |
| Гомография | «Карта-переводчик» между наклонённой картинкой камеры и ровной схемой поля сверху. Благодаря ей программа понимает расстояния на поле, а не только номера пикселей. |
| Фильтр Калмана | Математическое сглаживание. Он соединяет несколько наблюдений мяча, чтобы единичный дрожащий кадр не заставил робота резко дёрнуться. Это не нейросеть. |
| Прогноз | Приближённый расчёт того, где мяч встретит линию каретки. Это полезная оценка, а не гарантированное предсказание будущего. |
| PWM / ШИМ | Число, задающее долю мощности мотора. В этом проекте для движения каретки — от 0 до 255. |
| ESC | Электронный контроллер бесколлекторного двигателя толкателя. Он получает импульсы длительностью примерно 1000–2000 микросекунд. |
| Pico SDK | Набор инструментов и библиотек, с которыми собирается программа для Raspberry Pi Pico. |
| Прошивка | Программа внутри Pico. После сборки она получается в файле `.uf2`. |
| `.env` | Обычный текстовый файл с настройками в виде `ИМЯ=ЗНАЧЕНИЕ`. В нём нет программного кода. |
| Виртуальное окружение (`.venv`) | Изолированная папка Python-зависимостей для одного проекта. Её можно удалить и создать заново. |

## 4. Безопасность до первого включения

Движущийся робот — это не только программа. Ошибка в проводах, направлении
мотора или настройке мощности может заставить каретку резко поехать. Поэтому:

1. Сначала убедитесь, что питание можно быстро отключить одной рукой.
2. Первую проверку выполните без мяча и с поднятыми ведущими колёсами либо на
   механически безопасной малой мощности.
3. Перед подачей питания отправьте ручную команду стопа `S`.
4. Не меняйте номера пинов Pico и значения ESC «наугад».
5. Не оставляйте робот работающим без оператора.
6. Если что-то ведёт себя неожиданно — нажмите кнопку остановки, отключите
   питание и только потом разбирайтесь с кодом.

В программе есть две страховки:

- компьютер посылает `S`, если потерян мяч, метка робота, камера или программа
  завершается;
- Pico прекращает движение, если не получает корректную команду дольше
  `PICO_COMMAND_TIMEOUT_MS` миллисекунд из `.env`.

## 5. Что понадобится

### Компьютер

- Linux-компьютер (команды Bluetooth ниже ориентированы на Linux);
- Python 3.10 или новее;
- доступ в интернет только для первой установки Python-пакетов;
- USB-камера, которую видит система;
- Bluetooth-модуль HC-06, связанный с Pico.

### Робот

- Raspberry Pi Pico;
- собранная механика, моторный драйвер и питание;
- подключённые по вашей схеме моторы, кнопка, светодиод и, если используется,
  ESC толкателя;
- возможность перевести Pico в режим загрузчика: удерживать `BOOTSEL` при
  подключении USB.

### Перед началом проверьте

- камера смотрит на поле сверху и её крепление не шатается;
- мяч имеет хорошо заметный цвет;
- метка каретки имеет другой хорошо заметный цвет;
- на поле нет цветных предметов такого же цвета, как мяч или метка;
- Pico отключён от опасной нагрузки на время первой прошивки.

историю проекта.

## 7. Первичная установка на компьютере

### 7.1 Получите исходный код

Если проект ещё не скачан:

```bash
git clone https://github.com/Kirill-DoS/wasserschwein.git
cd wasserschwein
```

Если он уже есть, просто откройте терминал в его корневой папке. Проверить это
можно так:

```bash
ls README.md .env.example requirements.txt
```

Команда должна показать все три файла.

### 7.2 Создайте свои настройки

```bash
cp .env.example .env
```

`.env.example` остаётся нетронутым: это общий шаблон. `.env` — ваша локальная
копия с параметрами именно вашего робота. Откройте `.env` в любом текстовом
редакторе и сначала проверьте хотя бы `CAMERA_ID`, `BT_PORT` и `BT_HC06_MAC`.

### 7.3 Создайте окружение Python и установите библиотеки

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install -r requirements.txt
```

Что произошло:

- первая команда создала папку `.venv`;
- вторая включила её только для текущего окна терминала;
- третья обновила установщик пакетов;
- четвёртая поставила `numpy`, `opencv-python` и `pyserial`.

Когда окружение включено, начало строки терминала обычно содержит `(.venv)`.
После закрытия терминала включите окружение снова:

```bash
cd /путь/к/wasserschwein
source .venv/bin/activate
```

Чтобы выйти из него, выполните `deactivate`. Удалять `.venv` безопасно: при
необходимости создайте её повторно командами выше.

### 7.4 Быстрая проверка установки

```bash
python3 -m unittest discover -s tests -v
python3 tools/camera_index.py
```

Первая команда должна закончиться словом `OK`. Вторая переберёт доступные номера
камер. Если нужная камера находится, запомните её номер и запишите в
`CAMERA_ID` файла `.env`.

## 8. Единый файл настроек `.env`

### Главное правило

Все значения, которые обычно надо подстраивать под конкретный стенд, находятся
в одном месте — в корневом `.env`. Не ищите их в `vision/*.py` или в
`firmware/src/constants.h`.

Python читает `.env` при старте. При сборке Pico специальный скрипт создаёт
временный заголовок C в папке `firmware/build/`; исходники прошивки не
переписываются. Поэтому изменение настройки Pico вступает в силу только после
новой сборки и прошивки `.uf2`.

Формат строки простой:

```text
ИМЯ_НАСТРОЙКИ=значение
```

Не ставьте пробелы вокруг `=`. Строки, начинающиеся с `#`, — комментарии и ни
на что не влияют.

### 8.1 Камера и Bluetooth

| Настройка | Простое назначение | Когда менять |
| --- | --- | --- |
| `CAMERA_ID` | Номер камеры в Linux: обычно `0`, иногда `1`. | Камера не открывается или подключено несколько камер. |
| `CAMERA_WIDTH`, `CAMERA_HEIGHT` | Разрешение кадра. | Только если камера не поддерживает текущее разрешение. После изменения обязательно повторить разметку. |
| `CAMERA_FPS` | Желаемое число кадров в секунду. | Если камера реально умеет другое значение. |
| `BT_PORT` | Файл Bluetooth-порта, обычно `/dev/rfcomm0`. | Если вы подключили HC-06 к другому номеру. |
| `BT_BAUDRATE` | Скорость обмена компьютера с HC-06. | Только если она совпадающе изменена в модуле и Pico. |
| `BT_HC06_MAC` | Адрес конкретного HC-06. | На другом Bluetooth-модуле. |
| `COMMAND_RESEND_INTERVAL_S` | Как часто компьютер повторяет текущую команду. | Обычно не менять. Значение должно быть меньше тайм-аута Pico. |

### 8.2 Поле и поиск объектов

| Настройка | Простое назначение | Практический совет |
| --- | --- | --- |
| `FIELD_WIDTH_MM`, `FIELD_HEIGHT_MM` | Настоящие размеры игрового поля в миллиметрах. | Измерьте рулеткой. Неверные значения меняют масштаб скорости и расстояний. |
| `VIRTUAL_FIELD_WIDTH`, `VIRTUAL_FIELD_HEIGHT` | Размер внутренней плоской карты программы. | Не меняйте без необходимости; это не реальные миллиметры. |
| `BALL_HSV_LOWER`, `BALL_HSV_UPPER` | Нижняя и верхняя граница цвета мяча: три числа через запятую. | Обычно сохраняются автоматически после калибровки цвета. |
| `ROBOT_HSV_LOWER`, `ROBOT_HSV_UPPER` | Граница цвета метки каретки. | Подберите, если программа не видит робота или видит посторонний предмет. |
| `BALL_TIMEOUT_S` | Сколько секунд программа ещё терпит отсутствие мяча. | Меньше — безопаснее, но возможны лишние остановки. Начните с `0.25`. |
| `BALL_MIN_RADIUS_PX`, `BALL_MAX_RADIUS_PX` | Допустимый радиус мяча на кадре в пикселях. | Измените, если камера поднята/опущена и мяч стал заметно больше/меньше. |
| `BALL_MIN_AREA_PX` | Минимальная площадь пятна мяча. | Увеличьте, если блики ошибочно считаются мячом. |
| `BALL_MIN_CIRCULARITY` | Насколько пятно должно быть похожим на круг. | Увеличьте, если программа ловит длинные цветные полосы. |
| `ROBOT_MIN_RADIUS_PX`, `ROBOT_MAX_RADIUS_PX` | Допустимый размер цветной метки каретки. | Подстраивайте аналогично мячу. |
| `ROBOT_TRACKER_FILTER_LENGTH` | Сколько последних положений метки сглаживать. | Больше — плавнее, но медленнее реакция. |

### 8.3 Прогноз мяча

Эти параметры не являются «магическим ИИ». Это ручные числа приближённой
модели движения:

| Настройка | Что делает |
| --- | --- |
| `BALL_CURVATURE_K` | Добавляет небольшой изгиб траектории в модели. Если поле ровное и мяч катится прямо, можно уменьшать к нулю. |
| `BALL_FRICTION` | Насколько быстро модель уменьшает скорость мяча из-за трения. |
| `BALL_RESTITUTION` | Какая доля скорости остаётся после удара о боковую стену. `1` — очень упругий удар, меньше `1` — мяч замедляется. |
| `BALL_MAX_SIM_STEPS` | Максимальная длина расчёта будущей траектории. Обычно не требует изменения. |
| `BALL_HISTORY_LENGTH` | Сколько точек прошлого пути рисовать для отладки. На управление почти не влияет. |
| `BALL_MIN_PREDICTION_SPEED_MM_S` | Скорость, ниже которой мяч считается почти стоящим. |
| `BALL_STOP_SPEED_MM_S` | Скорость, ниже которой расчёт будущего пути прекращается. |

Если робот систематически едет не туда, сначала проверьте разметку поля и
цветовую маску. Только затем осторожно настраивайте эти числа по одному.

### 8.4 Движение каретки

| Настройка | Что делает | Как менять |
| --- | --- | --- |
| `CONTROLLER_MAX_SPEED_MM_S` | Самая большая желаемая скорость каретки в миллиметрах в секунду. | Начните с меньшего значения и повышайте только после безопасных тестов. |
| `CONTROLLER_MAX_ACC_MM_S2` | Насколько быстро каретка имеет право разгоняться и тормозить. | Меньше — мягче движение; больше — резче реакция. |
| `CONTROLLER_DEADBAND_MM` | Зона около цели, в которой робот не пытается «ловить каждый миллиметр». | Увеличьте, если каретка дрожит около цели. |
| `MOTOR_MAX_PWM` | Верхняя граница мощности мотора, обычно не больше `255`. | Временно уменьшите для первых испытаний. |

### 8.5 Pico, пины и таймер безопасности

Настройки с префиксом `PICO_` нужны при сборке прошивки. Они не меняют
работающий Pico сами по себе: после изменения выполните сборку, скопируйте новый
`.uf2` и перезагрузите контроллер.

| Группа | Настройки | Что это |
| --- | --- | --- |
| Двигатель каретки | `PICO_MOTOR_WRAP`, `PICO_MOTOR_FREQ_HZ` | Технические параметры PWM. Обычно оставьте как есть. |
| ESC толкателя | `PICO_SERVO_WRAP`, `PICO_SERVO_DIVIDER`, `PICO_ESC_*` | Диапазоны и рабочие импульсы ESC. Меняйте только по документации именно вашего ESC. |
| Безопасность | `PICO_COMMAND_TIMEOUT_MS`, `PICO_CALIBRATE_ESC_ON_BOOT` | Таймер остановки и флаг калибровки ESC при запуске. Калибровка по умолчанию выключена (`0`). |
| Связь | `PICO_UART_BAUDRATE`, `PICO_PIN_TX`, `PICO_PIN_RX` | Скорость UART и пины, к которым подключён HC-06. Скорость должна совпадать с `BT_BAUDRATE`. |
| Остальная плата | `PICO_PIN_LED`, `PICO_PIN_BUTTON`, `PICO_PIN_SERVO1`, `PICO_PIN_SERVO2`, `PICO_PIN_MOTOR_LEFT`, `PICO_PIN_MOTOR_RIGHT`, `PICO_PIN_BATTERY` | Номера физических выводов Pico. Менять только после проверки схемы. |

> `PICO_CALIBRATE_ESC_ON_BOOT=1` включает процедуру калибровки ESC при каждом
> старте. Это может привести к неожиданным импульсам на механизме. Для обычной
> игры оставляйте `0`.

### 8.6 Необязательные настройки YOLO

Обычная игра эти значения не использует. Они нужны только сценариям из
`tools/ml/`, если вы решите экспериментировать с нейросетью.

| Настройка | Что делает |
| --- | --- |
| `YOLO_MODEL` | Имя базовой модели, которую скачает библиотека YOLO. |
| `YOLO_CONFIDENCE` | Насколько уверенным должно быть распознавание при черновой авторазметке. Больше — меньше ложных находок, но больше пропусков. |
| `YOLO_DEFAULT_EPOCHS` | Сколько проходов по датасету делает обучение по умолчанию. |
| `YOLO_IMAGE_SIZE`, `YOLO_BATCH_SIZE` | Размер изображения и число изображений, обрабатываемых одновременно. Большее значение требует больше памяти GPU. |
| `YOLO_FREEZE_LAYERS`, `YOLO_PATIENCE`, `YOLO_WORKERS` | Технические параметры обучения. Без опыта оставьте исходные значения. |
| `YOLO_VALIDATION_FRACTION`, `YOLO_RANDOM_SEED` | Доля картинок для проверки и фиксированное «зерно» случайности, чтобы разделение можно было повторить. |

### 8.7 Что появляется после калибровки

В `vision/calibration/` лежат файлы геометрии. Они описывают, как камера видит
конкретное поле. Файл `geometry.json` создаётся автоматически и не хранится в
Git, поскольку зависит от камеры и её положения. Если камера сдвинулась,
изменили высоту, зум или разрешение — удалите этот файл и проведите разметку
заново:

```bash
rm vision/calibration/geometry.json
```

Удалять `.npy` из поставки обычно не нужно. Разметчик перезапишет их при новой
калибровке.

## 9. Сборка и прошивка Raspberry Pi Pico

### 9.1 Установите инструменты

Нужны компилятор для ARM, CMake, Make, Python и Pico SDK. На Debian/Ubuntu
обычно достаточно:

```bash
sudo apt update
sudo apt install build-essential cmake git gcc-arm-none-eabi libnewlib-arm-none-eabi python3
git clone https://github.com/raspberrypi/pico-sdk.git "$HOME/pico/pico-sdk"
cd "$HOME/pico/pico-sdk"
git submodule update --init
```

На другой системе установите аналогичные пакеты привычным менеджером пакетов.
Pico SDK можно разместить в другом месте — важно только правильно указать путь
в следующем шаге.

### 9.2 Соберите файл прошивки

Вернитесь в папку проекта. В `.env` укажите реальный путь к SDK и папку, куда
Linux подключает Pico в режиме BOOTSEL. Например:

```text
PICO_SDK_PATH=/home/ivan/pico/pico-sdk
PICO_MOUNT_POINT=/run/media/ivan/RPI-RP2
```

Затем убедитесь, что `.env` создан, и соберите прошивку:

```bash
cd /путь/к/wasserschwein
test -f .env && echo ".env найден"
make -C firmware all
```

Во время сборки CMake читает `.env`, создаёт временный файл
`firmware/build/generated/generated_env.h`, а затем компилирует прошивку. Это
нормально: временный заголовок не нужно редактировать руками.

Если всё прошло успешно, итоговый файл будет здесь:

```text
firmware/build/arcanoid_main_file.uf2
```

Для повторной сборки после изменения исходников или `.env`:

```bash
make -C firmware fast
```

Сборка видит изменение `.env` и заново создаёт временный заголовок настроек
автоматически. Всё равно убедитесь, что потом загрузили новый `.uf2` именно в
Pico: пересборка сама по себе не меняет уже прошитый контроллер.

Если CMake «запомнил» старый путь к SDK или вы сильно меняли настройки сборки,
сделайте чистую сборку:

```bash
make -C firmware clean
make -C firmware all
```

### 9.3 Загрузите `.uf2` в Pico

1. Отключите Pico от USB.
2. Зажмите кнопку `BOOTSEL` на Pico.
3. Не отпуская её, подключите USB к компьютеру.
4. В системе появится диск `RPI-RP2`.
5. Скопируйте на него файл `.uf2`.

Например, если диск смонтирован как `/run/media/имя/RPI-RP2`:

```bash
cp firmware/build/arcanoid_main_file.uf2 /run/media/имя/RPI-RP2/
```

После копирования Pico сам перезагрузится и запустит новую прошивку. Цель
`make -C firmware deploy` делает такую копию автоматически только если
`PICO_MOUNT_POINT` в `.env` соответствует вашей системе.

### 9.4 Важное правило после изменения `.env`

- Изменили `CAMERA_*`, HSV, размеры поля или параметры каретки — перезапустите
  Python-программу.
- Изменили любой `PICO_*` или `MOTOR_MAX_PWM` — пересоберите и заново прошейте
  Pico.
- Изменили `BT_BAUDRATE` или `PICO_UART_BAUDRATE` — значения должны быть
  одинаковыми, иначе связь не заработает.

## 10. Подключение Bluetooth

Этот раздел рассчитан на HC-06, подключённый к UART Pico. Сначала узнайте MAC
адрес модуля; в Linux это можно сделать через настройки Bluetooth или командой
`bluetoothctl devices`. Запишите адрес в `BT_HC06_MAC` файла `.env`.

Создайте последовательный Bluetooth-порт:

```bash
sudo rfcomm connect 0 "$(grep '^BT_HC06_MAC=' .env | cut -d= -f2)" 1
```

После успешного подключения должен существовать файл `/dev/rfcomm0`. Если у вас
другой номер, измените и команду, и `BT_PORT` в `.env`.

Проверка:

```bash
ls -l /dev/rfcomm0
```

Окно с `rfcomm connect` обычно оставляют открытым на время игры. При отключении
связи программа Pico всё равно должна остановить каретку по таймеру безопасности.

## 11. Проверка без движения робота

Не начинайте с автоматического запуска. Сначала проверим отдельные части.

### 11.1 Камера

```bash
source .venv/bin/activate
python3 tools/camera_index.py
```

Если скрипт нашёл камеру с номером `1`, измените строку в `.env`:

```text
CAMERA_ID=1
```

### 11.2 Настройки Pico без компиляции

Эта команда проверяет, что генератор может прочитать `.env` и создать C-заголовок:

```bash
python3 tools/generate_firmware_env.py --env .env --output /tmp/generated_env.h
```

Успешный запуск ничего не печатает и создаёт `/tmp/generated_env.h`. Ошибка с
названием настройки означает: добавьте эту строку в `.env`, сверившись с
`.env.example`.

### 11.3 Ручная команда Bluetooth

Сначала убедитесь, что колёса свободны от пола или мощность ограничена. Затем:

```bash
python3 -m vision.bluetooth_cli S
python3 -m vision.bluetooth_cli F 30
python3 -m vision.bluetooth_cli S
```

Команды означают:

| Команда | Значение |
| --- | --- |
| `S` | Немедленно остановить каретку и ESC. |
| `F 0` … `F 255` | Движение в одном направлении с указанной мощностью. |
| `B 0` … `B 255` | Движение в обратном направлении. |
| `L 1000` … `L 2000` | Импульс левому ESC толкателя. |
| `R 1000` … `R 2000` | Импульс правому ESC толкателя. |

Если направление оказалось обратным ожидаемому, остановите робот. Не
компенсируйте это случайной заменой букв во многих файлах: сначала проверьте
проводку и логику направления в `vision/main.py`, затем внесите одно осознанное
изменение и перепроверьте команды `F` и `B`.

## 12. Калибровка камеры и поля

Калибровка отвечает на вопрос: «какая точка на картинке соответствует какой
точке на настоящем поле?». Без неё программа не может безопасно перевести
пиксели в миллиметры.

### 12.1 Когда её нужно делать

Сделайте новую разметку, если:

- камеру сдвинули, повернули, подняли или опустили;
- изменили разрешение `CAMERA_WIDTH` / `CAMERA_HEIGHT`;
- поменяли объектив или зум;
- заменили поле или заметно передвинули стены/рейку.

### 12.2 Запуск разметки

Если калибровки нет, `vision.main` сам её попросит. Чтобы принудительно начать
заново, удалите метаданные:

```bash
rm vision/calibration/geometry.json
python3 -m vision.main
```

В появившемся окне кликайте точки в том порядке, в котором просит программа:

1. углы поля — последовательно по кругу;
2. точки правой стенки;
3. точки левой стенки;
4. две точки линии, по которой ездит каретка.

Не спешите: чем точнее вы укажете реальные границы, тем лучше будет перевод
координат. Клавиша `U` отменяет последнюю ошибочную точку. После успешной
разметки данные сохранятся в `vision/calibration/`.

### 12.3 Настройка цвета мяча

После геометрии откроется окно с ползунками HSV. Белым цветом показывается то,
что программа считает мячом.

1. Положите мяч на обычное место на поле.
2. Меняйте ползунки, пока белым не останется мяч, а фон и блики не исчезнут.
3. Нажмите `Enter`, чтобы сохранить выбранный диапазон в `.env`.
4. Нажмите `Esc`, чтобы отменить изменение.

Если освещение в комнате сильно меняется, проводите калибровку при том же
свете, при котором будет игра. Для метки робота диапазон `ROBOT_HSV_*` пока
задаётся напрямую в `.env` — подберите его тем же принципом.

## 13. Полный запуск игры

Перед запуском должны быть готовы: `.env`, включённое окружение Python,
загруженная прошивка Pico, подключённый Bluetooth-порт и правильная калибровка.

В одном терминале:

```bash
cd /путь/к/wasserschwein
source .venv/bin/activate
sudo rfcomm connect 0 "$(grep '^BT_HC06_MAC=' .env | cut -d= -f2)" 1
```

В другом терминале:

```bash
cd /путь/к/wasserschwein
source .venv/bin/activate
python3 -m vision.main
```

В отладочном окне:

- зелёный круг и линия показывают найденный мяч и его недавние положения;
- синяя линия — рассчитанный будущий путь;
- красная точка — рассчитанная точка встречи;
- в терминале строки `[CMD]` показывают команду, ошибку в миллиметрах и

Остановить работу можно клавишей `Esc` в окне или `Ctrl+C` в терминале. В обоих
случаях программа пытается отправить `S`, закрыть Bluetooth и освободить камеру.

## 14. Автоматические тесты

Автоматические тесты проверяют небольшие куски логики без камеры, Bluetooth,
Pico и подключения питания. Поэтому их стоит запускать после каждого изменения
кода, но они не заменяют безопасную проверку реального устройства.

### 14.1 Обычный запуск

```bash
source .venv/bin/activate
python3 -m unittest discover -s tests -v
```

Ожидаемый финал:

```text
----------------------------------------------------------------------
Ran ... tests in ...s

OK
```

Сейчас тесты проверяют регулятор каретки:

- **мёртвую зону**: рядом с целью каретка не должна дёргаться;
- **ограничение ускорения**: команда не должна прыгать от нуля к максимуму за
  один кадр;
- **ограничение PWM**: мощность не выходит за безопасный диапазон;
- **аварийный сброс**: после сброса старая команда движения не сохраняется.

Отдельный тест проверяет шаблон `.env.example`: из него должен без ошибок
создаваться заголовок с обязательными настройками Pico. Это защищает от ситуации,
когда в документации есть новая настройка, а в шаблоне её забыли.

### 14.2 Проверка синтаксиса

Эта команда не запускает робота. Она убеждается, что Python может прочитать
файлы как программу:

```bash
PYTHONPYCACHEPREFIX=/tmp/wasserschwein-pycache python3 -m compileall -q vision tools tests
```

Если команда ничего не вывела и вернула вас в приглашение терминала — синтаксис
проверен. Кэш помещается в `/tmp`, поэтому не загрязняет проект.

### 14.3 Проверка `.env` для прошивки

```bash
python3 tools/generate_firmware_env.py --env .env --output /tmp/generated_env.h
```

Это быстрая проверка обязательных параметров `PICO_*`. Она особенно полезна до
долгой сборки на другом компьютере.

## 15. Проверки с настоящим железом

Выполняйте пункты строго по порядку. Следующий этап — только после успешного
предыдущего.

1. **Стоп без движения.** Выполните `python3 -m vision.bluetooth_cli S`. Pico
   должен принять команду без неожиданного движения.
2. **Малая мощность.** На поднятых колёсах отправьте `F 30`, затем `S`. Повторите
   для `B 30`. Проверьте направление и остановку.
3. **Потеря связи.** Дайте небольшую команду движения и оборвите Bluetooth.
   Каретка должна остановиться примерно через `PICO_COMMAND_TIMEOUT_MS`.
4. **Камера и цвета.** Запустите полную программу без мяча. Робот не должен
   ехать. Положите мяч — в окне должен появиться только один зелёный круг.
5. **Потеря мяча.** Во время медленного движения закройте мяч рукой. Не позднее
   `BALL_TIMEOUT_S` программа должна послать `S`.
6. **Потеря метки.** Закройте метку робота. Поведение должно быть таким же:
   остановка, а не движение по последнему положению.
7. **Медленная игра.** Пустите мяч медленно, наблюдая траекторию в окне.
8. **Рабочая скорость.** Только после предыдущих пунктов постепенно поднимайте
   `MOTOR_MAX_PWM`, `CONTROLLER_MAX_SPEED_MM_S` и ускорение.

Запишите результаты каждого теста: дата, значение параметра, направление,
время остановки, замечания. Это намного полезнее, чем менять сразу десять чисел
и пытаться угадать причину.

## 16. Как настраивать поведение робота

### Робот дрожит рядом с точкой

Увеличьте `CONTROLLER_DEADBAND_MM` небольшими шагами, например на 5–10 мм.
Мёртвая зона означает: очень близко к цели мелкая ошибка игнорируется, чтобы
мотор не менял направление каждую долю секунды.

### Робот слишком резко стартует или тормозит

Уменьшите `CONTROLLER_MAX_ACC_MM_S2`. Если он остаётся вялым даже после плавной
настройки, медленно повышайте `CONTROLLER_MAX_SPEED_MM_S`. Всегда начинайте с
низкого `MOTOR_MAX_PWM`.

### Робот не успевает за мячом

Сначала проверьте механику: люфт, ремень, питание, трение, реальную скорость.
Затем увеличивайте по одному `MOTOR_MAX_PWM`, максимальную скорость и ускорение.
Не пытайтесь «исправить» слабый мотор параметрами прогноза мяча.

### Программа видит блики вместо мяча

Сузьте `BALL_HSV_LOWER`/`BALL_HSV_UPPER`, увеличьте `BALL_MIN_AREA_PX` или
`BALL_MIN_CIRCULARITY`. Лучше сначала улучшить освещение и фон: хороший сигнал
всегда надёжнее сложной обработки.

### Программа часто теряет настоящий мяч

Проверьте контраст мяча с полем, фокус камеры и диапазон HSV. Если мяч заметно
изменился в кадре из-за высоты камеры, подстройте `BALL_MIN_RADIUS_PX` и
`BALL_MAX_RADIUS_PX`. Увеличивать `BALL_TIMEOUT_S` стоит осторожно: большой
тайм-аут означает более долгую езду по устаревшим данным.

### Прогноз не похож на настоящий отскок

Сначала повторите калибровку и проверьте размеры поля. Потом сделайте несколько
медленных запусков мяча и настройте `BALL_FRICTION` и `BALL_RESTITUTION` по
одному. `BALL_CURVATURE_K` лучше оставить небольшим или нулевым, пока не ясно,
какое физическое явление он моделирует на вашем поле.

## 17. Что было исправлено и почему

Ниже — не просто список изменений, а причины, почему они важны для реального
робота.

### 17.1 Одни координаты для разметки и игры

**Было.** Поле могло размечаться на одном разрешении, а обработка мяча идти на
другом. Один и тот же номер пикселя тогда означал разные места изображения.

**Риск.** Гомография (карта-переводчик координат) строилась для одной картинки,
а применялась к другой. Робот мог ехать к неверной точке.

**Исправлено.** Камера запрашивается в разрешении из `.env` и оно записывается
в `geometry.json`. Если кадр имеет другой размер, программа не начинает
движение и просит выполнить калибровку заново.

### 17.2 Робот больше не едет по «старому» мячу

**Было.** Сглаживание движения могло продолжать рисовать прогноз после того,
как настоящий мяч пропал из кадра.

**Риск.** Старое положение превращалось в ложную цель, например когда мяч
закрыли рукой или камера на мгновение потеряла изображение.

**Исправлено.** После `BALL_TIMEOUT_S` прогноз сбрасывается, регулятор
обнуляется и посылается `S`. Фильтр Калмана теперь помогает пережить короткий
шум, но не имеет права командовать роботом бесконечно долго без настоящего мяча.

### 17.3 Миллиметры отделены от мощности мотора

**Было.** Одна величина использовалась и как скорость на поле (мм/с), и как PWM
(0–255).

**Риск.** Это разные единицы измерения. Настройка становилась непредсказуемой:
изменение физической скорости могло случайно ломать мощность мотора.

**Исправлено.** Регулятор сначала получает желаемую скорость в мм/с, ограничивает
разгон, а затем переводит результат в PWM в пределах `MOTOR_MAX_PWM`.

### 17.4 Расчёт движения выполняется один раз на кадр

**Было.** Внутреннее состояние регулятора могло обновляться дважды для одного
изображения.

**Риск.** Программа мысленно разгоняла робот быстрее, чем происходило время в
реальном мире. Это приводило к рывкам.

**Исправлено.** На каждом кадре вычисляется реальная разница времени `dt`, а
команда движения рассчитывается один раз.

### 17.5 Отражение мяча от стен

**Было.** Когда расчёт доходил до боковой стены, путь мог оборваться.

**Риск.** В игре мяч обычно отражается, поэтому точка встречи после отскока
получалась неверной.

**Исправлено.** Скорость по горизонтали меняет знак на стене и уменьшается по
коэффициенту `BALL_RESTITUTION` (упругость отскока).

### 17.6 Pico страхует потерю связи

**Было.** При зависшем Python или обрыве Bluetooth последняя команда мотора могла
оставаться активной.

**Риск.** Каретка продолжала движение без компьютера, который её контролирует.

**Исправлено.** В прошивке есть watchdog. Если корректных команд нет дольше
`PICO_COMMAND_TIMEOUT_MS`, каретка останавливается. Пока связь исправна,
компьютер повторяет текущую команду с периодом `COMMAND_RESEND_INTERVAL_S`.

### 17.7 Калибровка ESC не запускается сама

**Было.** Автоматическая калибровка ESC при включении могла происходить рядом с
собранным механизмом.

**Риск.** ESC воспринимает импульсы как команды, а неожиданная последовательность
при старте опасна.

**Исправлено.** По умолчанию в `.env` стоит `PICO_CALIBRATE_ESC_ON_BOOT=0`.
Включайте `1` только для отдельной осознанной процедуры по инструкции ESC, затем
сразу верните `0`, пересоберите и прошейте Pico.

### 17.8 Все настройки собраны в `.env`

**Было.** Параметры были разбросаны по Python, JSON и заголовкам C. Их легко было
забыть изменить в одном месте или случайно сохранить чужие настройки в Git.

**Риск.** Непонятно, какое значение реально работает, а настройка Pico отличалась
от настройки компьютера.

**Исправлено.** `.env` — единственная точка настройки. Python читает его прямо,
а сборка Pico безопасно генерирует временный заголовок из тех же значений.
`.env.example` показывает полный перечень без личных параметров.

### 17.9 Структура проекта стала понятнее

**Было.** Исходники, 3D-модели, скрипты и служебные файлы лежали рядом или в
папках с неочевидными названиями.

**Риск.** Новому человеку трудно понять, что запускать, что прошивать, а что
является моделью корпуса. В Git попадали виртуальные окружения и временные
файлы.

**Исправлено.** Код зрения — в `vision/`, Pico — в `firmware/`, модели — в
`hardware/`, утилиты — в `tools/`, документация — в `docs/`. `.gitignore`
исключает `.venv`, системные файлы и результаты сборки.

## 18. Дополнительные утилиты и YOLO

### Полезные утилиты

| Команда | Назначение |
| --- | --- |
| `python3 tools/camera_index.py` | Ищет доступные номера камер. |
| `python3 tools/hsv_tuner.py` | Открывает отдельный инструмент подбора HSV. |
| `python3 tools/check_gpu.py` | Проверяет GPU для необязательных ML-экспериментов. |
| `python3 -m vision.bluetooth_cli S` | Отправляет единственную безопасную ручную команду стопа. |

### Что такое YOLO и нужен ли он

YOLO — это семейство нейросетей для распознавания объектов на изображении. Ей
нужно много размеченных фотографий, обучение и обычно более мощный компьютер.
Для этого робота она не обязательна: цветовой поиск быстрее настраивается и
проще объясняется. Используйте YOLO, только если простой поиск цвета уже не
справляется с освещением или внешним видом мяча.

Для эксперимента:

```bash
source .venv/bin/activate
python3 -m pip install -r requirements-ml.txt
python3 tools/ml/auto_label.py --help
python3 tools/ml/create_validation_split.py --help
python3 tools/ml/train.py --help
```

Автоматическая разметка — только черновик. Всегда проверьте каждую рамку вокруг
мяча вручную до обучения модели. Docker-файлы в корне относятся к этим
необязательным экспериментам и не нужны для обычной игры.

## 19. Типичные неполадки

| Симптом | Вероятная причина | Что сделать |
| --- | --- | --- |
| `Не найден .env` | Не создан локальный файл настроек. | Выполните `cp .env.example .env`. |
| `No module named cv2` | Не включено или не заполнено `.venv`. | `source .venv/bin/activate`, затем `python3 -m pip install -r requirements.txt`. |
| Камера не открывается | Неверный `CAMERA_ID`, камера занята другой программой. | Запустите `tools/camera_index.py`, закройте другие программы с камерой. |
| Программа просит калибровку | Нет `geometry.json` или разрешение не совпадает. | Проведите разметку заново; не меняйте разрешение после неё. |
| Мяч не находится | Неверный HSV, блики, плохой фокус. | Настройте HSV, освещение и размеры мяча в пикселях. |
| Робот не находится | Неверный цвет метки или её закрывает механизм. | Подберите `ROBOT_HSV_*`, сделайте метку крупнее/контрастнее. |
| `could not open port /dev/rfcomm0` | Bluetooth-порт не создан или указан неверно. | Выполните `rfcomm connect`, проверьте `BT_PORT`. |
| Pico не реагирует | Не совпадают UART-пины или скорость связи. | Сверьте схему, `PICO_PIN_TX/RX`, `BT_BAUDRATE` и `PICO_UART_BAUDRATE`; пересоберите прошивку. |
| Pico не собирается | Не задан/неправилен `PICO_SDK_PATH`. | Проверьте строку в `.env`, затем выполните чистую сборку. |
| Каретка не останавливается | Это аварийная ситуация. | Отключите питание. Затем проверьте `S`, таймер Pico и проводку драйвера до следующего запуска. |
| Команда `make ... deploy` не копирует файл | Другой путь монтирования Pico. | Скопируйте `.uf2` вручную или исправьте `PICO_MOUNT_POINT` в `.env`. |

## 20. Как обновлять проект

Перед обновлением сохраните свой `.env` отдельно: он специально не хранится в
Git. Затем:

```bash
git pull
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

Сравните свой `.env` с новым `.env.example`: если в шаблоне появились новые
строки, добавьте их в свой файл. После изменений `PICO_*` пересоберите и
перепрошейте Pico. После любых изменений кода запустите тесты:

```bash
python3 -m unittest discover -s tests -v
```

Не добавляйте `.env`, `.venv`, `firmware/build/` и временные калибровочные файлы
в коммит. Они относятся к вашему локальному стенду, а не к исходному коду.
