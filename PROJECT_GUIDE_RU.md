# Понятное руководство по проекту Wasserschwein

## 1. Что это за робот

Это робот для игры, похожей на «Арканоид». На поле лежит мяч. Робот ездит влево
и вправо по своей рейке и должен оказаться там, куда прилетит мяч. Камера висит
над полем и смотрит вниз. Компьютер принимает решения, а Raspberry Pi Pico
выполняет их мотором.

```text
Камера → поиск мяча и робота → прогноз → команда Bluetooth → Pico → мотор
```

Здесь нет обязательного искусственного интеллекта. Основной способ поиска —
сравнение цвета: программа ищет на кадре пиксели выбранного цвета (**HSV-маска**).
Это быстро и подходит, когда мяч и метка робота хорошо отличаются от поля.

## 2. Небольшой словарь

- **Кадр** — одна фотография, которую камера выдаёт много раз в секунду.
- **HSV** — способ описать цвет: оттенок, насыщенность и яркость. Он удобнее
  обычного RGB, когда мы ищем предмет заданного цвета.
- **Гомография** — перевод картинки камеры в плоскую карту поля. Благодаря ей
  программа получает не «500 пикселей», а примерно «900 мм от края».
- **Фильтр Калмана** — аккуратный прогноз следующей позиции по нескольким
  предыдущим наблюдениям. Представьте, что камера иногда дрожит или один кадр
  пропустил мяч: фильтр не верит одному кадру слишком сильно и продолжает
  движение плавно. Это не магия и не нейросеть, а математическое сглаживание.
- **PWM (ШИМ)** — число от 0 до 255, которое задаёт мощность мотора.
- **ESC** — контроллер бесколлекторного мотора толкателя.
- **Watchdog** — таймер безопасности: если команды перестали приходить,
  контроллер сам останавливает мотор.

## 3. Из чего состоит проект

| Папка или файл | Простое назначение |
| --- | --- |
| `CV/main.py` | Главная программа: камера, решение, Bluetooth. |
| `CV/BallTracker.py` | Находит мяч и рассчитывает, куда он движется. |
| `CV/RobotTracker.py` | Находит цветную метку на каретке робота. |
| `CV/Polygon.py` | Помогает мышью отметить поле и рейку на кадре. |
| `CV/RobotController.py` | Плавно разгоняет и тормозит каретку. |
| `software/src` | Прошивка Raspberry Pi Pico. |
| `3D_models` | Модели деталей и сборок FreeCAD/3MF. |

## 4. Что было проблемой и как исправлено

### Разные размеры изображения

**Проблема.** Поле размечалось на большом кадре 1280×720, а мяч искался на
уменьшенном 640×360. Одни и те же координаты означали разные точки изображения.
Из-за этого карта поля (**гомография**) могла отправить робота не туда.

**Исправление.** Разметка и рабочий трекинг используют один размер кадра.
Программа сохраняет этот размер в `CV/geometry.json` и отказывается ехать, если
камера сейчас выдаёт другой размер. После переноса камеры или смены разрешения
нужно провести разметку заново.

### Робот ехал по старому мячу

**Проблема.** Когда мяч исчезал из кадра, прогноз (**фильтр Калмана**) продолжал
рисовать его предполагаемую позицию слишком долго. Робот мог поехать к мячу,
которого камера уже не видит.

**Исправление.** Если настоящего обнаружения нет дольше 0,25 секунды, прогноз
сбрасывается, компьютер посылает `S`, а внутренний регулятор обнуляет скорость.

### Смешивались миллиметры и мощность мотора

**Проблема.** Старый регулятор использовал одно число и как скорость в мм/с, и
как PWM 0…255. Это как считать расстояние в метрах и одновременно называть его
процентом громкости: формула выглядит правдоподобно, но физически неверна.

**Исправление.** Теперь регулятор сначала выбирает линейную скорость каретки
в мм/с, ограничивает разгон, затем переводит её в PWM. Для точной настройки
следует измерить настоящую скорость каретки при PWM 50, 100, 150 и 200 и
подстроить `max_speed_mm_s` и `max_acc_mm_s2` в `CV/config.json`.

### Два расчёта движения за один кадр

**Проблема.** Регулятор обновлялся дважды для одного изображения, поэтому
мысленный разгон происходил вдвое быстрее.

**Исправление.** Теперь команда рассчитывается один раз на каждый кадр и
использует настоящее время между кадрами.

### Мяч «исчезал» у стены

**Проблема.** При достижении боковой стены прогноз останавливался, хотя в игре
мяч должен отразиться.

**Исправление.** Скорость по горизонтали меняет знак, а часть энергии теряется
по коэффициенту отскока (**restitution**). Значение можно менять в `config.json`.

### Обрыв Bluetooth не останавливал каретку сам

**Проблема.** Если Python зависал, Pico мог оставить последнюю скорость мотора.

**Исправление.** В прошивке добавлен watchdog: через 400 мс без корректной
команды каретка тормозит. Некорректные команды также вызывают остановку. Пока
робот движется нормально, компьютер повторяет последнюю команду каждые 100 мс,
поэтому watchdog видит, что связь жива.

### ESC калибровался при каждом включении

**Проблема.** Автоматическая последовательность калибровки ESC при старте могла
быть неожиданной рядом с движущимся механизмом.

**Исправление.** Калибровка при старте выключена. Для осознанной калибровки
нужно временно изменить `CALIBRATE_ESC_ON_BOOT` на `1`, прошить Pico и вернуть
значение обратно после процедуры.

### Запуск был непонятным

**Проблема.** README указывал несуществующий файл из неправильной папки, а
зависимости были сохранены в неудобной кодировке.

**Исправление.** Добавлены UTF-8 `requirements.txt`, отдельный список для YOLO,
команды запуска, тестов и сборки. Все пути рабочего кода строятся относительно
папки `CV`, а не текущего терминала.

## 5. Подготовка компьютера

Нужны Linux, Python 3.10+, USB-камера и Bluetooth HC-06. В корне проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Подключите HC-06. MAC-адрес в команде замените на адрес своего модуля:

```bash
sudo rfcomm connect 0 98:D3:11:FD:1C:0B 1
```

Порт должен появиться как `/dev/rfcomm0`.

## 6. Первая калибровка

Запустите:

```bash
python3 CV/main.py
```

Если калибровки нет, появится окно. Кликните по углам поля в порядке по кругу,
затем по правой стенке, левой стенке и линии рейки робота. Ошибочную точку можно
отменить клавишей `U`. После геометрии выберите цвет мяча ползунками. Белое на
окне маски — то, что программа считает мячом.

Калибровку нужно повторить, если камера сдвинулась, изменила высоту, зум или
разрешение.

## 7. Ручная проверка связи

Сначала проверьте связь без игры:

```bash
python3 CV/BlueTooth.py S
python3 CV/BlueTooth.py F 50
python3 CV/BlueTooth.py S
```

Никогда не начинайте сразу с `255`. Убедитесь, что направления `F` и `B`
соответствуют реальному движению. Если они перепутаны, поменяйте их только в
одном месте — в `CV/main.py` рядом с созданием `direction`.

## 8. Сборка прошивки Pico

1. Установите [Pico SDK](https://github.com/raspberrypi/pico-sdk).
2. Укажите путь к SDK:

   ```bash
   export PICO_SDK_PATH=/путь/к/pico-sdk
   ```

3. Соберите:

   ```bash
   make -C software all
   ```

4. Зажмите BOOTSEL на Pico, подключите USB и скопируйте файл
   `software/build/arcanoid_main_file.uf2` на появившийся диск.

## 9. Тесты

Тесты проверяют математику регулятора без настоящего робота:

```bash
python3 -m unittest discover -s tests -v
```

Перед тестом с реальным железом проверьте:

1. `S` действительно останавливает каретку.
2. Отключение Bluetooth останавливает каретку примерно за 0,4 секунды.
3. Закрытие мяча рукой вызывает стоп примерно за 0,25 секунды.
4. После смены разрешения программа просит новую разметку.

## 10. YOLO — необязательный эксперимент

YOLO — это нейросеть для поиска объектов. Она не участвует в обычной игре,
потому что цветовой поиск быстрее и проще отлаживается. Эксперимент полезен,
если освещение нестабильно или цвет мяча нельзя выделить надёжно.

```bash
pip install -r requirements-ml.txt
python3 train.py --output ball_dataset
```

Сначала подготовьте реальные изображения и разметку. Автоматическая разметка
только создаёт черновик — её обязательно нужно проверять вручную.
